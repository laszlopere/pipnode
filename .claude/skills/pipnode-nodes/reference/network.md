# Network

Nodes in the **Network** category move data between the pipnode message graph and the outside world: HTTP services, MQTT brokers, public weather APIs, and a USB-attached Meshtastic LoRa radio. Every wire carries a `PnMessage` with an envelope (`topic` / `id` / `created`) plus a schemaless `data.*` bag whose three mandatory members are `data.value` (canonical numeric; booleans as 0.0/1.0), `data.output` (human-readable summary), and `data.success` (boolean). These nodes are I/O nodes: they do all work in pure C with no helper subprocesses (`curl` is the one exception, spawned by the HTTP family), they connect asynchronously off the main thread and marshal results back, and — because pipnode runs from a desktop launcher with no terminal — they report failures through the message contract (`success=FALSE` + a human-readable `output`/`error`) and a red `❗` node-body error state rather than to stderr. The MQTT nodes pull their broker URL and credentials from host-provisioned connection profiles (`PnProfileSchema` / `PnVault`), so secrets never live in the saved workflow file.

## Http Client

**Purpose** — Auto-triggered HTTP GET. Polls a configured URL once per `period` seconds and emits the response. `PnHttp` is also the base class for `PnRate` and `PnWeather`, which override its `is_configured` / `build_command` / `emit_message` vfuncs (`lib/pn-http.c:419`). Derives from `PnAutoTrigger`; the request is spawned with `curl --silent --show-error --location --max-time <period-1>` on the trigger's worker thread (`lib/pn-http.c:212`, spawn at `lib/pn-http.c:319`).

**When to use** — Periodically scrape a REST/JSON endpoint or health/metrics URL into the graph; downstream a Query / JMESPath / JSON Path node can pull fields out of the body. For weather specifically use the **Weather** subclass instead.

**Ports** — `has_input=FALSE`, `has_output=TRUE` (source only; `lib/pn-http.c:431`).

**Settings** — One GObject property `url` (string, default `NULL`/empty; `lib/pn-http.c:434`) plus the inherited `PnAutoTrigger` `period` (default 5 s; `PN_HTTP_DEFAULT_PERIOD`, `lib/pn-http.c:463`). The URL may embed `${nodeclass}` / `${nodename}` / `${hostname}`, expanded per request via `pn_node_expand_vars`; any other `${...}` is left verbatim (`lib/pn-http.c:218`). No connection profile — this node carries its URL inline. While the URL is empty the node sits in the red configuration-required state and emits nothing (the trigger early-returns on `!is_configured`, `lib/pn-http.c:309`).

**Emits / consumes** — Emission is timer-driven (one fetch per `period`). The emitted message fills: `url` (the fetched URL), `success` (TRUE only on curl-exited-OK **and** HTTP 2xx; `lib/pn-http.c:261`), `status` (HTTP status code, when > 0), and `output` (the response body, or empty on failure). Body/status are split apart from curl's `--write-out` sentinel by `pn_http_split_body_and_status` (`lib/pn-http.c:165`). Topic is the node default.

**Gotchas** — `curl --max-time` is capped one second below the period so a dead host can't stall the next tick. `url` is mutex-guarded because the worker reads it while the main thread may overwrite it (`lib/pn-http.c:45`). Help page (`data/help/PnHttp.html`) documents only `url`/`period` — the data-bag keys above are richer than the help text suggests.

## MQTT Source

**Purpose** — Source-only node: connects to an MQTT broker via libmosquitto, **subscribes** to a topic filter, and emits one `PnMessage` per delivered PUBLISH (`lib/pn-mqtt.c`). Derivable base type; subclasses hook `accept_topic` (network-thread topic filter) and `process_message` (`lib/pn-mqtt.c:1063`).

**When to use** — Ingest pub/sub telemetry (Zigbee2MQTT, Tasmota, Home Assistant, sensors) into the graph. Pair it with **MQTT Sink** (publish side) following the same primary profile to talk to the same broker with zero per-node setup. Use Source to **subscribe**, Sink to **publish**.

**Ports** — `has_input=FALSE`, `has_output=TRUE` (`lib/pn-mqtt.c:1071`).

**Settings** — Built around a `broker-profile` reference (`lib/pn-mqtt.c:1074`), tagged `pn_param_spec_set_profile_ref(..., PN_PROFILE_TYPE_MQTT_BROKER)`. The picker offers: **Default** (empty id → follows the type's primary `mqtt-broker` profile), a **named profile**, or **Custom settings**. Profile fields (`url`, `username`, `password`, `client-id`) live in the host vault (`Edit → Credentials`), defined by the schema in `lib/pn-mqtt-profile.c` (`pn_mqtt_register_profile_type`: Broker URL / Username / Password (secret) / Client ID, help page `MqttBrokerProfile.html`). The same-named **inline** properties are the node's "Custom settings" config (`pn_param_spec_set_profile_ref_inline_fields`, `lib/pn-mqtt.c:1088`) and are editable only in Custom mode — greyed and cleared otherwise. `password` is tagged `pn_param_spec_set_secret` so it is never serialized to the file (`lib/pn-mqtt.c:1117`). URL accepts `tcp://host[:port]` (1883), `ssl://`/`mqtts://host[:port]` (TLS, 8883, system trust store), or bare `host[:port]`. Non-profile rows: `subscribe-topic` (default `#` so it produces output immediately) and `qos` (0–2; `lib/pn-mqtt.c:1130`). There is **no built-in default broker URL** — empty until configured (the host vault supplies it).

**Emits / consumes** — Emission is broker-driven: each inbound PUBLISH builds a message via `pn_mqtt_build_message` (`lib/pn-mqtt.c:531`). The **envelope topic is the MQTT topic verbatim** (no prefix), so a downstream Filter matches what the broker published. Data bag: `payload` (parsed JSON value, or raw UTF-8 string, or "" for binary), `value` (payload as a number when it parses), `output` (one-liner naming the topic — payload not inlined), `success=TRUE`, `qos`, `retained`. A `#` subscribe at connect time can produce a retained-state flood; messages are queued on the network thread and drained in one main-loop idle batch, capped at `PN_MQTT_PENDING_MAX = 10000` (oldest dropped on overflow; `lib/pn-mqtt.c:313`).

**Gotchas** — Async connect: the node stays red (`has-error`) until a CONNACK + successful SUBSCRIBE lands on the main thread, not just a TCP socket (`lib/pn-mqtt.c:243`). Reconnect is automatic (1–30 s exponential back-off, re-subscribes every reconnect). Setters/vault changes coalesce into one debounced restart idle (`schedule_restart`, `lib/pn-mqtt.c:764`); the initial connect is deferred to `constructed()` so it runs after deserialization. Stale-session callbacks are dropped by a generation counter. Legacy inline credentials are migrated one-shot into a vault profile post-load (`lib/pn-mqtt.c:782`). A refused subscription (ACL denial) flips the node to error rather than a misleading healthy green.

## MQTT Sink

**Purpose** — Sink-only node: **publishes** each inbound message to an MQTT broker (`lib/pn-mqtt-sink.c`). The publish topic comes from the inbound envelope (or an explicit template); the payload from `data.payload` (or an explicit template). Derivable base; hooks `process_message` (reshape/drop before publish) and `report_error` (`lib/pn-mqtt-sink.c:1073`).

**When to use** — Drive MQTT devices/relays from the graph (e.g. `Tasmota Switch → Rewrite (topic = cmnd/${data/device}/POWER) → MQTT Sink`), or fan results back onto a broker. The counterpart to **MQTT Source**.

**Ports** — `has_input=TRUE`, `has_output=FALSE` (`lib/pn-mqtt-sink.c:1086`).

**Settings** — Same `broker-profile` / Default / named / Custom-settings model and the same vault-backed `url`/`username`/`password`(secret)/`client-id` inline fields as MQTT Source (`lib/pn-mqtt-sink.c:1100`). Publish-specific properties: `topic-template` (empty → use the inbound envelope topic; non-empty is expanded against node vars `${nodeclass}`/`${nodename}`/`${hostname}` and message fields `${path/to/field}` like `${data/device}`, plus document globals; `lib/pn-mqtt-sink.c:1159`), `payload` template (empty → publish `data.payload` verbatim — strings as raw bytes, structured values re-serialized to JSON; non-empty → expanded template bytes, e.g. `${data/value}` or a literal `ON`; `lib/pn-mqtt-sink.c:1173`), `retain` (boolean, `lib/pn-mqtt-sink.c:1187`), and `qos` (0–2). The inherited base `topic` row is hidden from the dialog via a settings schema flag since a Sink has no output port (`lib/pn-mqtt-sink.c:1093`).

**Emits / consumes** — Consumes inbound messages in `pn_mqtt_sink_receive` (`lib/pn-mqtt-sink.c:550`): resolves topic, builds payload (`pn_mqtt_build_payload`), then publishes. A message that yields no topic is dropped. Emits nothing (no output port) — publish failures surface only via the error funnel and red node body.

**Gotchas** — **Buffer-and-flush on startup**: while the session is down (the common case at document load, before the async connect completes) publishes are held in a bounded, timestamped offline queue and flushed oldest-first on connect, so an enforce-on-startup command still reaches the relay (`lib/pn-mqtt-sink.c:331`, `enqueue_pending` at `:312`). The queue is bounded by length (`PN_MQTT_SINK_QUEUE_MAX_LEN`, oldest evicted) and freshness (`PN_MQTT_SINK_QUEUE_MAX_AGE_US`, stale entries discarded on flush) — both live in `pn-mqtt-util.h` for unit-testing. A mid-flush link drop re-queues the remaining entries; a permanent rejection drops them. Since there is no output port, a `publish_error` flag flips the node to its error visual and is cleared on the next successful publish or reconnect (`lib/pn-mqtt-sink.c:121`). Errors are routed through the `report_error` vfunc funnel (`lib/pn-mqtt-sink.c:181`) → `pn_node_log_error`, so a subclass can observe them. Same debounced-restart / generation / legacy-migration / async-connect machinery as MQTT Source.

## Weather

**Purpose** — Auto-triggered source that polls current weather for a named place from one of two free, key-less providers — Open-Meteo (global, default) or Bright Sky (DWD, Germany / central Europe). A specialised `PnHttp` subclass (`lib/pn-weather.c:135`): each tick first geocodes the city to lat/lon, then fetches the forecast — two HTTP requests, so it overrides `PnHttp`'s trigger while reusing the curl worker for the forecast leg (`pn_weather_trigger`, `lib/pn-weather.c:650`).

**When to use** — Show current conditions on a worksheet (wire into a Weather Report sink, Debug, Graph, or Query node). Choose Bright Sky only for German/central-European locations; Open-Meteo otherwise.

**Ports** — `has_input=FALSE`, `has_output=TRUE` (`lib/pn-weather.c:1083`).

**Settings** — `city` (string, default empty; place name like "Berlin" or "Berlin, US"; `lib/pn-weather.c:1088`) and `provider` (enum Open-Meteo / Bright Sky, rendered as a combobox, serialized by nick; `lib/pn-weather.c:1096`). Inherits `url` from `PnHttp` (the forecast endpoint, defaulted per provider and exposed so an advanced user can point at a self-hosted Open-Meteo; the geocoding endpoint stays fixed) and `period` (default 600 s / 10 min; `PN_WEATHER_DEFAULT_PERIOD`). **No connection profile** — the providers are key-less. Geocoding is handled by the shared `lib/pn-geocode.c` (`pn_geocode_resolve_sync`, city → lat/lon via Open-Meteo), cached until the city changes (`lib/pn-weather.c:580`). While the city is empty the node is in the red configuration-required state and does not poll. Changing `city` or `provider` kicks a refresh within seconds rather than waiting a full period (`pn_auto_trigger_kick`).

**Emits / consumes** — Timer-driven. On success: `success=TRUE`, `value` = current temperature °C (canonical), `temperature` (same, named), `humidity` (%), `wind_speed` (km/h), `weather_code` (WMO integer, Open-Meteo only), `description` (human label), `city`/`country` (resolved place), `latitude`/`longitude`, `status` (HTTP), `output` (one-line summary), and `raw` (the provider's full JSON response verbatim, deep-copied, so a downstream Query/JMESPath/JSON Path node can read any unpromoted field). On geocode failure: a message with `city`, `success=FALSE`, and a specific `output` reason (rate-limit / network / "no such place"). See `pn_weather_emit_message` (`lib/pn-weather.c:763`).

**Gotchas** — Failures are reported as a specific human-readable `output`, never to a terminal: `weather_format_http_error` distinguishes curl transport failure, HTTP 429 rate-limit, provider error bodies (`reason`/`detail`), and Bright Sky's "no nearby station" 404 (translated into "switch to Open-Meteo") (`lib/pn-weather.c:493`). All geocode-cache fields are mutex-guarded (worker vs property setter, `lib/pn-weather.c:109`). Lat/lon are formatted with `g_ascii_dtostr` so a non-`.` locale doesn't corrupt the request URL.

## Meshtastic

**Purpose** — Bidirectional bridge between the message graph and a USB-attached Meshtastic LoRa device (`lib/pn-meshtastic.c`, settings dialog in `lib/pn-meshtastic-gui.c`). Speaks the device's `0x94 0xC3`-framed protobuf serial protocol natively in C — no helper subprocess — holding the port open for the node's lifetime. Inbound `TEXT_MESSAGE_APP` packets land on the output port the moment they arrive; messages on the input port are sent as text on the configured channel.

**When to use** — Receive and send off-grid LoRa mesh text. As a source: feed received radio messages into the graph. As a sink: send graph messages out over the mesh (input `data.output` is the text to send, same convention as Text to Speech / Sound).

**Ports** — `has_input=TRUE`, `has_output=TRUE` — both (`lib/pn-meshtastic.c:1938`).

**Settings** — `device` (serial-port path like `/dev/ttyUSB0`; empty leaves it disconnected; `lib/pn-meshtastic.c:1941`) and `channel` (case-sensitive channel name; empty → primary channel index 0; `lib/pn-meshtastic.c:1947`). Both setters restart the worker thread. There is **no connection profile and no vault** here — the device is a local serial port, not a credentialed network service; the dialog's device combobox is populated from `pn_meshtastic_list_devices()` (shared USB VID:PID scan in `pn-mesh-discover`) and the channel combobox from the live handshake cache (`pn_meshtastic_get_channel_cache`). Four read-only, non-serialized runtime properties drive the dialog status row and node visual: `busy`, `hw-model` (HardwareModel enum from the handshake), `last-busy-path` (sticky EBUSY path), and `last-error` (sticky non-EBUSY failure) — all `G_PARAM_READABLE` so the JSON serializer skips them (`lib/pn-meshtastic.c:1958`). The property editor / class tab are installed by the GUI tier (`pn_meshtastic_gui_install`).

**Emits / consumes** — A single worker thread per node owns the fd, runs a config handshake at startup (channel list + node-name table + hw model), then multiplexes serial reads against a wake pipe, also sending an empty `ToRadio.heartbeat` every 5 minutes so the firmware keeps forwarding packets (`lib/pn-meshtastic.c:1421`). Each inbound text packet is emitted with topic `meshtastic` and data bag: `output` (message text), `success=TRUE`, `from_node_id` (`!aabbccdd` hex), `from_long_name` (display name or hex fallback), `channel_index`, `channel_name`, `packet_id`, `rx_time`, `hop_limit`, `hop_start`, `broadcast` (`lib/pn-meshtastic.c:1351`). On the input side, `pn_meshtastic_receive` reads `data.output` as the text to send and queues it on the outbox; messages with no `data.output` string are dropped silently; if not connected, dropped (`lib/pn-meshtastic.c:1725`).

**Gotchas** — Pure C protobuf codec, no subprocess. Connection errors surface via an emitted `success=FALSE` + `error` message **and** a sticky `last_error` that flips the node body to the red `❗` warning visual (`emit_error_message`, `lib/pn-meshtastic.c:1325`) — never to a terminal. A busy device (EBUSY: held by another node/process) auto-reverts `device` to "" and the combo to "No Device", but `last_busy_path` keeps the "Device … is busy." banner visible. Serial access needs `dialout` (or `uucp`) group membership or the open fails EACCES. The worker takes `flock(LOCK_EX)` exclusivity (shared transport `pn-mesh-serial`); a successful handshake clears any prior busy/error banner. Worker stops/restarts on `device`/`channel` change and on the disabled-flag toggle.
