# Network (bundled plugin)

Nodes from the in-tree **`plugins/network`** plugin (loadable module `pipnode_network.so`). This is a **separate, out-of-process plugin** that ships in the same source tree as pipnode and installs into `$pkglibdir/plugins/` where the host's default search path picks it up at startup (`pn-network-plugin.c:16-29`). It is **distinct from the core "Network" category** documented in [`network.md`](network.md): the core MQTT Source/Sink, Http Client, Weather, and Meshtastic nodes live in `lib/` and are compiled into libpipnode itself. **Ping and DNS Check used to be built-in**; they were moved here to demonstrate that the plugin ABI can ship first-party node types separately from the core binary (`pn-network-plugin.c:24-28`). MQTT Source/Sink stayed in core because their base class is meant to be subclassed across plugin boundaries (`pn-network-plugin.c:51-56`).

All four nodes register in `pn_plugin_init` (`pn-network-plugin.c:63-66`) in palette order: Ping, DNS Check, HTTPS Tunnel Receiver, HTTPS Tunnel Sender. The plugin also declares one host-provisioned credential profile type, **`http-basic`** ("HTTP Basic Auth"), shared by the two tunnel nodes — fields `username` (string) and `password` (secret), help page `HttpBasicAuthProfile.html`, registered via `pn_network_register_profile_types` (`pn-network-profiles.c:20-33`, constant `PN_NETWORK_PROFILE_HTTP_BASIC = "http-basic"` at `pn-network-profiles.h:30`). The `mqtt-broker` schema is **not** here — it lives in core.

All four sit in the palette's **Network** category. They report failures through the message contract / `pn_node_log_*` and a red `❗` node-body error state (`pn_node_set_has_error`), never to a terminal.

## Network Ping
**Purpose** — Auto-triggered reachability probe. Once per `period` it shells out to the system `ping(1)` (`ping -c 1 -W <timeout> <host>`) on the inherited worker thread and emits one message reporting whether the host answered and the round-trip time. `PnPing` derives from `PnAutoTrigger` (`pn-ping.c:43`); trigger at `pn-ping.c:160`, spawn at `pn-ping.c:196`.
**When to use** — Periodically check whether a host/IP is up and how fast it responds; wire into Debug, a gauge, or a TTS sink (the `output` is a spoken-sentence summary).
**Ports** — `has_input=FALSE`, `has_output=TRUE` (source only; `pn-ping.c:348-349`).
**Settings** — One property `host` (string, default `NULL`/empty; hostname or IP; `pn-ping.c:351`) plus inherited `period` (default **5 s**, `PN_PING_DEFAULT_PERIOD`, `pn-ping.c:375`). No connection profile. While `host` is empty the node sits red (`has-error`) and emits nothing — the trigger early-returns (`pn-ping.c:182-186`). `NULL`/`""` are the same unconfigured state; `host` is mutex-guarded (worker reads, main thread writes; `pn-ping.c:39, 104`).
**Emits / consumes** — Timer-driven. Bag: `host` (the probed host), `success` (boolean, from ping's exit status; `pn-ping.c:212`), `value` (RTT in ms, **only set when a `time=` token was parsed** out of stdout; `pn-ping.c:121, 219-220`), and `output` (a TTS-friendly sentence — "The host X is reachable, round trip time N milliseconds." / "…is not reachable.", with sub-ms and singular-ms special cases; `pn-ping.c:226-260`). Raw ping stdout is deliberately **not** propagated.
**Gotchas** — Uses the unprivileged system `ping`, so it needs **no CAP_NET_RAW** (`pn-ping.c:153-156`). `-W` per-reply timeout is capped one second below the period so a dead host can't delay the next tick. Host is shell-quoted (`g_shell_quote`). Icon fa-wifi `U+F1EB`, body blue; unconfigured shows the central red `❗`.

## DNS Check
**Purpose** — Auto-triggered resolver-health probe. Once per `period` it runs `dig +short +time=<t> +tries=1 [@server] <name>` for each configured name and reports how many resolved. `PnDns` derives from `PnAutoTrigger` (`pn-dns.c:40`); trigger at `pn-dns.c:260`, per-name `dig` in `query_one` (`pn-dns.c:190`).
**When to use** — Monitor whether a specific DNS server (or the system resolver) is healthy. Deliberately uses `dig`, not `getaddrinfo`/NSS, so `/etc/hosts` or mDNS can't mask a broken DNS server (`pn-dns.c:184-189`).
**Ports** — `has_input=FALSE`, `has_output=TRUE` (source only; `pn-dns.c:437-438`).
**Settings** — Two properties plus inherited `period` (default **30 s**, `PN_DNS_DEFAULT_PERIOD`, `pn-dns.c:473` — relaxed so it doesn't flood a public resolver): `server` (string, default empty; DNS server host/IP — **empty falls back to the system resolver** in `/etc/resolv.conf`, the `@`-arg omitted; `pn-dns.c:440`) and `names` (string, default empty; whitespace- **or** comma-separated list looked up each tick, split on `", \t\r\n"`; `pn-dns.c:447`). Only `names` governs configuration — `server` is optional (`pn-dns.c:55-58`). No connection profile. While `names` is empty the node is red and emits nothing. Both strings mutex-guarded.
**Emits / consumes** — Timer-driven. Bag: `server` (the queried server, or the literal `"system"` when empty; `pn-dns.c:313-315`), `success` (boolean, **TRUE only when all names resolved**, `n_ok == n_total`; `pn-dns.c:316`), `ok_count` (int), `name_count` (int), `results` (a JSON object mapping each name → boolean; `pn-dns.c:302-322`), and `output` (one-line summary; `pn-dns.c:324-343`).
**Gotchas** — `dig` exits 0 even on NXDOMAIN/empty answer, so an empty (whitespace-only) stdout is treated as a **failed** lookup (`pn-dns.c:239-248`). Per-query timeout is capped one below the period then **divided across the batch** so all names fit in one tick. Server/names shell-quoted. Requires `dig` (bind9 dnsutils) on PATH. Icon fa-sitemap `U+F0E8`, body blue, red `❗` when unconfigured.

## HTTPS Tunnel Sender
**Purpose** — Sink that POSTs every inbound `PnMessage`, serialized as JSON `{"topic","id","created","data":{…}}`, to a target HTTPS URL via a long-lived libsoup `SoupSession`. The receiving end is an **HTTPS Tunnel Receiver** — together they relay messages pipnode-to-pipnode over HTTPS. `PnHttpsTunnelSender` derives from `PnNode` (`pn-https-tunnel-sender.c:73`); `receive` at `:322`, JSON body at `:115`, async POST `:382`. Type macros are `PN_HTTPS_CLIENT` / `PN_TYPE_HTTPS_TUNNEL_SENDER` (legacy "client" alias).
**When to use** — Send messages from one pipnode (or worksheet) to another over HTTPS; pair with an HTTPS Tunnel Receiver. Defaults pair zero-config with a same-machine Receiver.
**Ports** — `has_input=TRUE`, `has_output=FALSE` (sink only; `:564-565`). The inherited base `topic` row is hidden from the dialog (`PN_ROW_FLAG_HIDDEN`, `:567-572`).
**Settings** — `url` (string, default **`"https://127.0.0.1:8443/"`** — pairs with a same-machine Receiver; empty → red + drops messages; `:574, 640`); `auth-profile` (profile-ref to `http-basic`, default `""` = follow primary; `:587`, tagged `:595`); legacy inline `username` (`:598`) and `password` (tagged secret, never serialized; `:608, 614`); `verify-tls` (boolean, default **FALSE** — accepts the Receiver's self-signed cert out of the box; TRUE validates against the system trust store; `:616`). Credentials resolve from the referenced vault profile first, falling back to inline fields (`:190`). Auth is **preemptive Basic** — sets `Authorization: Basic …` directly when both user and pass are non-empty (`:212, 356-362`).
**Emits / consumes** — Consumes inbound messages (`:322`). No output port — emits nothing into the graph. Lights the processing glow across the whole POST round-trip. The response is drained and status-checked but discarded; non-2xx logs a warning, transport failure logs an error (`:277`).
**Gotchas** — Body always includes a `"data"` key even when empty, so the Receiver hits its structured-parse branch (`:151-171`). All config is main-thread only (no mutex; the SoupSession dispatches on the default `GMainContext`). Disposal cancels in-flight requests via a `GCancellable` (`:522-531`). One-shot post-load migration imports legacy inline credentials into an `http-basic` vault profile (`:467, 508`). Icon fa-paper-plane `U+F1D8`, body green; red `❗` when `url` is cleared.

## HTTPS Tunnel Receiver
**Purpose** — Source that runs an HTTPS `SoupServer` and emits one `PnMessage` per `POST` it receives, parsing the JSON body back into the envelope+data shape a Sender produced. The listening end of the tunnel pair. `PnHttpsTunnelReceiver` derives from `PnNode` (`pn-https-tunnel-receiver.c:91`); request handler `:585`, JSON→message `:507`, emits via `pn_node_emit_message` `:666`. Type macros `PN_HTTPS_SERVER` / `PN_TYPE_HTTPS_TUNNEL_RECEIVER` (legacy "server" alias).
**When to use** — Receive messages POSTed from a remote pipnode's HTTPS Tunnel Sender (or any HTTPS client) and inject them into the local graph. Works out of the box with an auto-generated self-signed cert.
**Ports** — `has_input=FALSE`, `has_output=TRUE` (source only; `:950-951`).
**Settings** — `port` (uint 0–65535, default **8443**; 0 disables the server; binding 443 needs root/CAP_NET_BIND_SERVICE; `:953`); `auth-profile` (profile-ref to `http-basic`, default `""` = follow primary; required of clients, but the **endpoint is left open when no credentials resolve**; `:962, 971`); legacy inline `username`/`password` (`:974, 983`; password tagged secret `:990`); `cert-path` (string, default **`$XDG_DATA_HOME/pipnode/default-cert.pem`**; `:992, 1037`) and `key-path` (default **`…/default-key.pem`**; `:1006, 1038`). Credentials resolve from the vault profile first, else inline (`:414`). **Every** setter, and a vault `changed` signal, calls `restart_server` (`:807-835, 883`).
**Emits / consumes** — Server-driven (one emit per POST). `build_message_from_json` (`:507`) copies `topic`/`id`/`created` onto the envelope and the entire `data` object onto the bag; a client may also POST a **flat** `{"foo":1}` with no `data` wrapper and it lands as `data.foo` (`:541-580`). Responds `{"ok":true}` (HTTP 200) to a valid POST; `GET /` returns a plain-text liveness banner; other methods → 405; empty/invalid/non-object body → 400 (`:620-657`). Runs synchronously on the default `GMainContext`.
**Gotchas** — Self-signed cert is **auto-minted** with GnuTLS (RSA-2048, `CN=pipnode`, ~10-year validity) on first start if the PEM files are missing, persisted (key chmod 0600) and reloaded later; clearing both paths uses an ephemeral in-memory cert cached for the node's lifetime (`:165, 300, 368`). Without resolved credentials the endpoint is **open/unauthenticated** — auth is only added when both user+pass are non-empty (`:732-741`). Basic-auth check is plain `g_strcmp0`, not constant-time (deliberate; `:451-459`). The server starts immediately in `init` (`:1050`); a failed `listen`/cert load logs an error and leaves the node red. Same one-shot legacy-credential migration as the Sender (`:847`). Icon fa-server `U+F233`, body green.
