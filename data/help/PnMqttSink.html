MQTT Sink

Group: Network. Type: PnMqttSink.

Input-only counterpart of MQTT Source. Holds a libmosquitto client open against a configured broker and PUBLISHes one MQTT message per incoming PnMessage. Closes the loop on a Source → filter → Sink flow without having to spawn a helper process or shell out through a command node.

Connection

The url property is the broker address; same syntax as MQTT Source — tcp://host[:port], ssl://host[:port] / mqtts://host[:port], or a bare host[:port] treated as plain TCP. The inline url is empty by default; with the Broker profile picker on its default the node follows the primary mqtt-broker profile, so a paired Source + Sink dropped onto a fresh worksheet reach the same broker without per-node configuration.

Connect is asynchronous; the body flips from red “configuration required” to green once the broker answers with a CONNACK. A transient outage triggers libmosquitto's built-in 1 s to 30 s exponential back-off reconnect — the visual state follows.

As on the MQTT Source, the broker can instead come from an mqtt-broker credential profile picked with the Broker profile selector: Default (…) uses the type's primary profile, a named profile uses that one, and Custom settings uses this node's own inline url/credentials (the profiles are ignored). The inline fields are editable only while Custom settings is selected; picking Default or a profile greys them out and clears them, so the picker's choice always survives save and reload.

Because the connect is asynchronous, a message can arrive in the brief window after a worksheet loads but before the broker session is up — most visibly the command a Tasmota Switch with enforce-on-startup emits the instant the document opens. Rather than lose it, the sink holds publishes in a small queue while offline and flushes them, oldest first, the moment it connects (the same applies across a mid-session reconnect). The queue is bounded: it keeps at most the 64 most recent publishes (the oldest is dropped when full), and on connect it only sends those still younger than 30 seconds — a command that has been waiting minutes is more likely stale than useful, while one from the load that just happened is exactly what you want enforced.

The backlog belongs to a particular broker. If you point the sink at a different broker while publishes are still queued — by editing the URL, picking another mqtt-broker profile, or clearing the broker entirely — the queued publishes are discarded rather than delivered to the new server: a command buffered for one broker is not silently misdelivered to another. Reconnecting to the same broker (a transient drop, or a profile edit that leaves the address unchanged) keeps the backlog, which is the whole point of the queue.

The backlog lives only in memory, for the life of the node. It is not saved with the worksheet and does not survive a restart. When the node is torn down — deleted, its worksheet closed, or the application quit — the sink makes one last best-effort flush if it is still connected, then discards anything left undelivered and notes the count in its log. So an offline backlog is a bridge across a brief reconnect, not a durable store-and-forward spool: if delivery across process restarts matters, give the broker a persistent session or publish through one that retains.

Publish topic

By default the publish topic is taken from each inbound message's topic envelope field. Per-message routing is then the upstream's concern: drop a Rewrite in front of the sink to stamp the topic you want, e.g. topic = cmnd/${data/device}/POWER for Tasmota relay control, and every message flows through with its own destination.

Alternatively, set the topic-template property to compute the publish topic on the sink itself. The template is expanded per message: ${nodeclass}, ${nodename}, and ${hostname} resolve against this node, while ${path/to/field} (such as ${topic} or ${data/device}) resolves against the incoming message JSON — a node variable wins over a message field of the same name. So cmnd/${data/device}/POWER or sensors/${hostname}/temp drive the broker topic without a separate Rewrite step. Leave it empty to use the envelope topic as before.

A straight MQTT Source → MQTT Sink bridge between two brokers republishes the inbound topic verbatim, and a synthesised cmnd/sonoff19/POWER from a Rewrite lands exactly as the user wrote it.

Messages without an envelope topic are dropped silently — there is no fallback topic, and MQTT wildcards (+, #) are never valid in a publish topic anyway.

Payload

The payload property is an optional template:

  • Empty — publish the inbound data.payload verbatim. String members go out as raw bytes; structured members (object, array, number, boolean) are serialised back to JSON so a Source → Sink relay between two brokers round-trips the original JSON shape.
  • Non-empty — expand the template against the message (same ${path/to/field} syntax as the topic) and publish its UTF-8 bytes. ${data/value} publishes a stringified number, ON / OFF publishes a fixed literal, and a JSON-shaped template publishes a synthetic JSON document.
Other knobs
PropertyDescription
retain Mark the publish as retained — the broker remembers the last retained value per topic and delivers it to every late subscriber on connect. Used for device state (Tasmota's own POWER publishes are retained for exactly this reason); leave off for transient events. To clear a retained topic, publish an empty payload with retain on (see Empty payloads below).
qos MQTT QoS for outgoing publishes (0 / 1 / 2). 0 is the right choice for high-rate telemetry, 1 for state changes you want acknowledged, 2 only when exactly-once matters and the broker / network can keep up.
username / password Optional MQTT auth, sent on the first CONNECT after they are set.
client-id MQTT client identifier. Empty asks libmosquitto to generate a random one. Use a different id from any paired MQTT Source on the same broker — two clients with the same id kick each other off.
Wiring example — Tasmota relay control
Switch (slide)
    → Rewrite
            topic   = cmnd/sonoff19/POWER
            data    = { "payload": "${data/value > 0 ? 'ON' : 'OFF'}" }
    → MQTT Sink

            retain  = false

The Rewrite step both stamps the destination topic on the envelope and reshapes the payload into the literal string the relay expects; the sink then publishes wherever the envelope points.

Empty payloads

An empty payload is published, not dropped — it goes out as a zero-length MQTT message. This is the standard way to clear a retained topic: send an empty data.payload (or a template that resolves to nothing) with retain on, and the broker forgets the retained value. The drop below applies only when the inbound message carries no data.payload member at all — that is treated as “nothing to publish” rather than as an intentional empty payload, so it is dropped instead of sending a misleading empty message.

What gets dropped

Messages are silently dropped (without warning) when:

  • The broker session is down and the message cannot be held for later — i.e. the offline queue is full of newer publishes (it caps at 64), or by the time the broker connects the message has aged past the 30 second freshness window. A publish that fits the queue and connects in time is delivered, not dropped (see Connection above).
  • The inbound message has no envelope topic.
  • No usable payload could be derived (no template set and no inbound data.payload).

A payload larger than the MQTT maximum — 268,435,455 bytes (~256 MB), the ceiling the protocol's length field allows — is also dropped, but with an error in the node's Log dialog rather than silently: it could never be published, so the sink refuses it up front instead of truncating it.
