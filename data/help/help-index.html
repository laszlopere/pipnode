Pipnode

Pipnode is a desktop visual flow editor inspired by Node-RED. You build wiring diagrams of data-processing nodes on the worksheet, save them as JSON files, and run them locally. Each node is a small object that produces, transforms or consumes messages; wires carry messages from one node's output to another node's input.

Interface overview

The main window is divided into three areas:

  • Palette (left sidebar) — a tree of every available node type, grouped by role. Drag a leaf onto the worksheet to create a node of that type. Right-click the palette header to open this help page.
  • Worksheet (centre) — the canvas where you arrange nodes and wire them together. Drag from a node's output port to another node's input port to create a wire. Double-click a node to edit its properties.
  • Debug pane (collapsible, bottom) — shows messages routed to Debug View by Debug nodes. Toggle it from View → Debug View.

Worksheets are saved as JSON via the File menu's New, Open, Save and Save As… entries. Loading a JSON worksheet recreates every node with its properties and reconnects the wires. The Save toolbar button and matching File → Save menu item are insensitive while the in-memory worksheet still matches its on-disk copy and ungate as soon as you make any edit (add or remove a node or wire, drag, toggle Disabled, or change a property in the Configure dialog); a successful save flips them back to insensitive. Save As… is always available so you can fork the same canvas under a new name without making a token edit first.

Any node can be temporarily switched off via the Disabled checkbox in its Configure dialog or the Enable/Disable entry in its right-click menu. Disabled nodes are drawn in grey, do not emit messages, ignore messages arriving on their input, and skip any periodic action (HTTP requests, ping probes, watchdog ticks). The state is persisted with the worksheet.

Worksheets and sheet tabs

A single .json file can carry several spreadsheet-style sheets, each rendering its own subset of nodes on its own tab. Sheets are organisational, not isolated execution units: every node on every sheet still runs in the same shared message-dispatch loop, so a Debug Print on Sheet 3 still receives ticks from an Auto Random on Sheet 1 as long as a wire connects them — with one important constraint, see below.

  • Tab strip. Sits across the top of the editor. Click a tab to switch sheets; click the trailing + button to add a fresh one (the dialog pre-fills the next free Sheet N name, so accepting with Enter is the common path). Drag a tab sideways to reorder it.
  • Right-click a tab for a context menu of Rename…, Move Left, Move Right, and Delete. Renaming a sheet rewrites the worksheet property of every node on it, so the tag stays consistent with the tab label after a save. Deleting a sheet removes every node it contains (and any wires touching them); the tab strip always carries at least one sheet, so the last one cannot be deleted.
  • New nodes dropped from the palette inherit the active sheet's name automatically. Pasting from the clipboard re-tags the pasted nodes onto the active sheet too, so you can move a subgraph between sheets with Cut + Paste.
  • Wires only connect nodes on the same sheet. The wire-drag handler refuses cross-sheet drops at creation time, and the file loader drops any cross-sheet wires it finds in a hand-edited save with a warning. Use a value-only Set stage on each side, plus a shared Format template, when you need to bridge sheets through a contract both halves agree on.
  • Save / Open / New operate on the whole file: one save writes every sheet at once, one load replaces every sheet, File → New resets the strip to a single empty sheet named Worksheet. The Save sensitivity tracks the modified flag for the file as a whole, not per sheet.
  • Headless runs. The pipnode-run binary loads every sheet's nodes together, exactly the way the GUI does — sheet tags are inert at runtime.

Files saved before the multi-sheet feature shipped load as a single sheet named Worksheet; the next save back-fills the new top-level "sheets" array next to the existing "nodes" and "connections" lists.

Messages and data flow

Every wire carries a PnMessage. The envelope properties are topic, id, created, plus a back-reference to the source node; the data bag is a JSON object the producer fills in with whatever payload it has to share. The bag is otherwise schemaless — any node may stash any extra keys it likes — but three members are mandatory on every message: data.value, data.output and data.success (see Standard data-bag members below). This is the contract that lets nodes mix and match without explicit configuration. A Graph fed from a Temp just works because both sides agree the canonical numeric reading lives at data.value; a Debug Print placed after a Format just works because both sides agree the human-readable summary lives at data.output.

The easiest way to see what a message looks like in practice is to wire one into a Debug Print set to JSON format — it renders the envelope and the data bag together as one indented object: 

{
  "from"    : "CPU Temperature",
  "from_id" : "5e2d1e17-1b06-4f3b-8d7a-2a05a8a93f0d",
  "topic"   : "/pnode/Temp/CPU Temperature",
  "id"      : "2405b0f6-f995-482e-888a-e42e540e1647",
  "created" : "2026-05-08T13:52:34.345410+02",
  "data"    : {
      "endpoint" : "thermal_zone0",
      "success"  : true,
      "value"    : 47.3,
      "output"   : "CPU temperature is 47.3 °C.",
      ...
  }
}

The from and from_id fields at the top are not properties of the message itself — they are synthesised by Debug Print at render time. from is the source node's display name (so a reader of the log immediately sees which node produced the line); from_id is the source node's stable, persistent UUID, suitable for unambiguous lookup when two nodes share a display name. The debug pane uses from_id to focus the originating node when its label is clicked. No other node ever sees these fields on a wire.

When a node's output has several wires hanging off it, each wire delivers its target an independent deep-copy of the emitted message rather than a shared pointer. A filter that mutates its received message in place (Table Model attaching data.table, Set rewriting members, Format rewriting data.output, …) therefore cannot contaminate a sibling branch — a Debug Print attached to the same source still sees what was emitted, not what a downstream filter rewrote it to. The id is preserved across the fork so the per-branch copies remain correlatable back to the original emission.

New nodes should honour these names when the concept applies and reach for a more specific name only when it genuinely does not. A node reporting a numeric reading puts the magnitude in value; the FX Converter node downstream multiplies that value in place rather than introducing a parallel converted_value, which is exactly why the Graph sitting after either of them needs no reconfiguration.

Envelope properties

FieldTypeMeaning
topicstring Routing tag every node stamps onto the messages it emits. Configured per node from the Node tab of the settings dialog as a template; the template is resolved at emit time and the substituted form is what the envelope carries. The default template is /pnode/${nodeclass}/${nodename} — or, for nodes that carry a hostname setting (every CPU / Memory / Load / Net I/O / Disk I/O / Connections probe and every shell / SSH-flavoured command), /pnode/${nodeclass}/${nodename}/${hostname} so the executing host appears in the topic.

Placeholders:

  • ${nodeclass} — the node type's display label (e.g. CPU, Clock).
  • ${nodename} — the per-instance name the user typed in the Name field; falls back to the class label when the user has not named the node.
  • ${hostname} — the node's configured hostname when it has one, or the executing machine's own hostname when the configured value is empty or "localhost". The substitution happens at the moment the message is created, so the same worksheet file carried between hosts produces topics that name the host the worksheet is running on.
The template itself is editable in place; an empty entry restores the built-in default. Topics not produced by a regular node resolution path stay in their original literal form: MQTT Source carries the broker-supplied topic verbatim, the HTTPS Tunnel Receiver replays the topic that arrived on the wire, and a Panel Input mouse click uses click/<button> (click/left, click/right, …).

Filter / transformer nodes (Format, Filter, FX Converter, Dedup, Edge, Throttle, JMESPath, Table Model) forward the message they received without rewriting the topic, so an FX Converter placed after a Temp carries the Temp's topic downstream.

idstring Unique identifier of the message, e.g. "2405b0f6-f995-482e-888a-e42e540e1647". Lasts for the lifetime of the message and never changes.
createdstring Timestamp marking when the message was created, in ISO-8601 format (e.g. "2026-05-08T13:52:34.345410+02").
fromstring Display name of the node that produced the message, e.g. "Pulse Balance".
from_idstring Stable per-node UUID of the producer, minted when the node was first created and preserved across save/load (and replaced with a fresh value on copy/paste so a clone never shares its origin's identity). Use this rather than from when you need an unambiguous reference — the debug pane drives its click-to-highlight on this field.

Standard data-bag members

Three members are mandatory: every message a node emits must carry data.value, data.output and data.success. They are the contract that lets unrelated nodes mix and match without explicit configuration — a Graph, a Debug Print, a Format template or a Filter can be wired to any producer and find what it needs. When the producer has no natural reading for one of them, supply a sensible stand-in rather than omitting the field: 0 for data.value on a node that fires purely as a trigger, the message's own descriptive text for data.output, and true / false for data.success reflecting whether the producing operation completed normally.

FieldTypeMeaning
data.valuenumber Mandatory. The headline numeric reading the message is about — whatever single number best summarises what the producer just observed. May be a JSON number, or a numeric string when the producer needs more range than a double provides (e.g. a hex-encoded JSON-RPC quantity, or an arbitrary-precision integer). Producers that have no natural number to report should emit 0 (or 1 / 0 as a boolean-style flag) rather than omitting the field.
data.outputstring Mandatory. A short, human-readable one-line summary of the message, suitable for showing in a log, a notification, or on screen.
data.successboolean Mandatory. Whether the producing operation completed normally. Nodes that cannot fail (pure latches, clocks, manual sources) emit true.

Checking the contract from a plugin

PnMessage exposes a virtual validate hook plus a pair of public wrappers so a plugin author can confirm an outgoing message satisfies the three-field contract before handing it to pn_node_emit(): 

gboolean   pn_message_validate   (PnMessage  *self, GError **error);
gboolean   pn_message_is_valid   (PnMessage  *self);
gboolean   pn_message_has_member (PnMessage  *self, const gchar *name);

pn_message_validate() returns TRUE when data.value (number, or numeric string for over-range producers), data.output (string) and data.success (boolean) are all present and well-typed. On failure it raises a PN_MESSAGE_ERROR whose code is either PN_MESSAGE_ERROR_MISSING_FIELD or PN_MESSAGE_ERROR_WRONG_TYPE and whose message names the first offending field — handy to wire to a g_warning() in a debug build: 

g_autoptr(GError) err = NULL;
if (!pn_message_validate (msg, &err))
    g_warning ("%s emitted a malformed message: %s",
               G_OBJECT_TYPE_NAME (self), err->message);
pn_node_emit (self, msg);

pn_message_is_valid() is a boolean shortcut for callers that only care about pass/fail. pn_message_has_member() is the underlying presence check, useful when a producer wants to fill in a stand-in only for a field it has not already set.

The check sits on the PnMessageClass.validate vfunc, so a subclass of PnMessage that adds its own mandatory state (for example, an image-carrying message requiring a non-NULL pixbuf) overrides the hook, chains up to the parent first so the universal contract is enforced, and then performs its own checks.

Beyond those three, several members are conventional within a family of nodes rather than universal across all of them:

Shape is { "header": { "cells": [ { "text": "..." }, ... ] }, "rows": [ { "cells": [ { "text": "..." }, ... ] }, ... ] }; the header member is omitted when the producer was told not to interpret a header. Each cell is a JSON object rather than a bare string so a future filter can decorate it with per-cell properties (colour, alignment, ...) without breaking the schema. Filled by the Table Model filter; downstream nodes (e.g. Set, Format) can index a row's cell by its column position and pull the cell's text member.

Producers are free to add any other members they need; consumers should ignore members they don't understand.

Large numeric vectors

Some producers have a whole array of doubles to share rather than a single reading — a sampled waveform, an FFT magnitude spectrum, an audio block, potentially megabytes of samples. Storing that as a JSON array would box every element in its own heap node (tens of bytes each instead of eight, no contiguity) and, worse, pay a full deep-copy on every wire fan-out. Pipnode keeps such payloads out-of-band instead: the buffer lives in a reference-counted PnVector attached to the message, and the data bag merely references it through a small, self-describing marker object: 

"samples" : { "$pnvector": 1, "len": 4096, "dtype": "f64" }

The marker is ordinary JSON, so it nests anywhere a value can — a top-level member, a nested object, an array element — and a vector-blind consumer (a Debug Print, the D-Bus inspection API, a generic logger) sees a sane {len, dtype} descriptor rather than a wall of numbers. A vector-aware node resolves the marker to the underlying buffer: 

PnVector *vec = pn_message_resolve_vector (msg,
                    pn_message_get_member (msg, "samples"));
if (vec != NULL) {
    const gdouble *x = pn_vector_get_data (vec);   /* contiguous f64 */
    gsize          n = pn_vector_get_len  (vec);
    ...
}

A producer attaches one with pn_message_set_vector(), which registers the buffer and writes the marker in a single call: 

g_autoptr(PnVector) vec = pn_vector_new_take (samples, n);  /* adopts buf */
pn_message_set_vector (msg, "samples", vec);
Marker fieldTypeMeaning
$pnvectorint The integer handle that ties the marker to its buffer in the message's vector registry. $pnvector is a reserved data-bag member name and a reserved object key — do not use it for anything else.
lenint Number of elements in the buffer.
dtypestring Element type. Currently always "f64" (IEEE-754 double); the field exists so other element types can be added later without changing the marker shape.

Vectors are immutable and shared. Because a single buffer is referenced by every fan-out branch, fan-out is a cheap reference bump rather than a copy — but that also means a node must never mutate a vector it received in place, or it would corrupt the copies its siblings hold. A node that transforms a vector allocates a new PnVector (with a new handle and marker) for its output and leaves the input untouched. This is the same copy-on-write discipline the rest of the message contract relies on: each wire delivers an independent clone of the envelope and the markers, and the clone shares the very same backing buffers until someone replaces a marker outright.

Serialization. When a message crosses a serialization boundary (the D-Bus automation API today; never the document save, since messages are not persisted), the out-of-band buffers have to travel with it or the handles would dangle. pn_message_serialize() takes an include_blobs flag for exactly that choice:

  • Descriptor-only (include_blobs = FALSE) emits just the envelope and its markers — a compact, inspectable shape that never base64-encodes megabytes by accident. This is the default for inspection paths such as the D-Bus GetLastOutputMessage; the rehydrated message keeps the marker but pn_message_resolve_vector() returns NULL for it (the payload was deliberately left behind).
  • Full (include_blobs = TRUE) additionally externalises every referenced buffer into a sibling blobs section keyed by handle, each entry a base64-encoded, little-endian f64 payload { "dtype", "len", "b64" } so pn_message_deserialize() can rebuild the buffers byte-for-byte on any host.
{
  "type"   : "PnMessage",
  "topic"  : "/pnode/Signal/Generator",
  "data"   : {
      "samples"  : { "$pnvector": 1, "len": 4, "dtype": "f64" },
      "success"  : true,
      "value"    : 0,
      "output"   : "4096-sample block"
  },
  "blobs"  : {
      "1" : { "dtype": "f64", "len": 4, "b64": "AAAA…" }
  }
}

A blob whose decoded byte count does not match len × 8 is rejected with a PN_MESSAGE_ERROR rather than silently yielding a short buffer, so a truncated or tampered payload fails loudly.

Vectors in the Calculator. The Calculator expression nodes treat a $pnvector input as a plain bag of numbers — not a mathematical vector, so there is no dot product, norm or other linear-algebra behaviour. Every operator just does the scalar thing to the numbers:

  • Scalar OP vector (and vice-versa) broadcasts: the scalar is applied to every element, giving a new vector. 2 * [1, 2, 3] → [2, 4, 6].
  • Vector OP vector is elementwise: [2, 3, 4] * [3, 4, 5] → [6, 12, 20].
  • On a length mismatch the result is as long as the longer operand, and each surplus tail element (where the shorter operand has run out) passes through verbatim: [2, 3] * [3, 4, 5] → [6, 12, 5] — the 5 is taken as it was. This is a deliberate choice rather than an error; it is operator-agnostic (the element passes through unchanged regardless of + - * /).
  • Functions (sin, cos, sqrt, …) map over a vector element by element: sin([a, b]) → [sin a, sin b].
  • Comparisons (< > <= >= == !=) behave differently: a vector comparison always reduces to a single scalar 1.0/0.0, true only when every compared element passes (all()-semantics). So [3, 5, 4] > 2 is 1.0 but [1, 5, 3] > 2 is 0.0, and the result stays usable as a gate driving an ordinary scalar sink. When two vectors of unequal length are compared, the surplus tail has no counterpart and counts as vacuously true.

A computation that yields a vector is written back to data.value as a fresh $pnvector marker (a new buffer, never a mutation of a shared input); a scalar result — including every comparison — is written as a plain number. A multi-line program can bind and emit vector intermediates the same way it does scalars.

Producing and consuming vectors. Two nodes bracket this machinery as a worked example. Ramp is a generator: its from, to and N inputs produce a $pnvector of N evenly-spaced values — the raw signal to experiment on. Reduce is its dual: it folds a vector back down to one scalar (sum / mean / min / max / range / count / product / stddev / first / last), re-entering the scalar world the rest of a flow lives in. With the Calculator in between for element-wise maths, a whole pipeline fits on one worksheet: ramp(0, 2π, 256) → sin(value) → reduce max. To look at a vector at any point, wire it into a Debug Print sink, which previews it as a short bounded sample rather than dumping every number; or feed it to the Oscilloscope, a green-phosphor CRT sink that traces the whole waveform on screen and fits it automatically.

Document globals

A worksheet file can carry a set of document globals: user-defined, typed name → value pairs that belong to the document as a whole rather than to any single node. They are shared by every sheet in the file and round-trip through the on-disk format, so a value you set is still there the next time the file is opened. Edit them from File → Document Settings…, on the Globals page; adding, changing or removing one marks the file modified so the change persists on the next save.

Each global holds one of four scalar types, picked from the type drop-down next to its value:

  • Boolean — true / false.
  • Integer — a 64-bit whole number.
  • Double — a floating-point number.
  • String — free text.

Their main use is as ${name} placeholders, the same ${…} syntax used for topic templates and the text / JSON templates of the Format, Rewrite and Notify nodes. A global is consulted as a fallback: each call site tries its own source first — the node's own variables (${nodeclass} / ${nodename} / ${hostname}) for a topic, or the incoming message's fields (${data/…}, ${topic}) for a template — and only when a name is not found there does it resolve against the document globals.

What happens to a name that no source provides depends on the call site: a topic template and the Rewrite node leave it exactly as typed (${name}), so an unrelated placeholder such as a shell one-liner's ${HOME} survives untouched, while the Format and Notify templates drop it to nothing.

So a global named env set to "prod" lets every node in the document fold the same value into its topics and templates — /pnode/${nodeclass}/${nodename}/${env} resolves the class and instance names from the node and ${env} from the global — and changing it in one place updates the whole document.

Credentials and connection profiles

Nodes that reach a service — an MQTT broker, an HTTP endpoint — need a host address and sometimes a username, password, or token. Pipnode keeps these out of your workflow files: a node stores only a reference, and the real values live in a private store on your machine. This means a saved .json never contains a secret, so you can share or commit it safely.

The unit of configuration is a profile. Each plugin that needs credentials declares one or more profile types (the bundled network plugin declares MQTT Broker and Web Service Login); you create named profiles of a type and fill in their fields. Open the manager from Edit → Credentials, pick a type on the left, and use Add to create a profile. Secret fields (passwords, keys) are masked with a reveal toggle; permission fields are checkboxes that default to off and must be granted explicitly.

A node picks its profile in its settings dialog — the field shows a drop-down of the profiles of the right type, plus an Edit… button onto the manager. The first entry, Default, follows the type's primary profile (mark one as Primary in the manager). So the common case — one broker for everything — needs no per-node setup: every node left on Default uses the primary. To talk to a second server, create another profile and select it on just that node.

When a profile type has a Help button next to its heading in the credentials manager, the plugin that declared the type has shipped a setup guide for it: how to install the remote subsystem (set up the broker, enable the device's API, …) and where to find the values that go in each field. Plugin authors register that page through pn_profile_schema_set_help_page() on the schema; without it the button is hidden. The bundled MQTT Broker and HTTP Basic Auth types both ship one as a worked example.

The store is a single file, ~/.config/pipnode/credentials.json, created with owner-only permissions (mode 0600), separate from your preferences. Editing a profile takes effect immediately — a connected node reconnects on the spot. On a server with no editor you can write that file directly, or supply a value through an environment variable (PIPNODE_PROFILE_<PROFILE-ID>_<FIELD>, upper-cased), which overrides the stored value; see the README and INSTALL files for the headless details.

Plugins

Pipnode can load extra node types from third-party shared objects at startup, so you can ship your own nodes without forking the source tree. A plugin is a single .so (or .dylib / .dll on macOS / Windows) that exports one C symbol — pn_plugin_init — which the host calls to register its #PnNode subclasses with the process-wide node factory.

Where pipnode looks for plugins

At startup both pipnode and pipnode-run scan, in order:

  1. Every directory listed in PIPNODE_PLUGIN_PATH (colon-separated, front-most takes precedence — useful while developing a plugin against an installed pipnode).
  2. $XDG_DATA_HOME/pipnode/plugins/ (falling back to ~/.local/share/pipnode/plugins/) — drop a .so here for a per-user install.
  3. The system plugin directory baked in at build time ($pkglibdir/plugins/, typically /usr/lib/pipnode/plugins/) — used by distribution packages.

A missing directory is silently treated as "no plugins here". A plugin found through two overlapping search paths is loaded only once.

Writing a plugin

Build against the pipnode headers and link the result as a loadable module (libtool's -module -avoid-version or its CMake / Meson equivalent). The minimal plugin is roughly: 

#include <gmodule.h>
#include <pipnode/pn-node.h>
#include <pipnode/pn-message.h>
#include <pipnode/pn-node-factory.h>
#include <pipnode/pn-plugin.h>

#define MY_TYPE_ECHO (my_echo_get_type ())
G_DECLARE_FINAL_TYPE (MyEcho, my_echo, MY, ECHO, PnNode)

struct _MyEcho { PnNode parent_instance; };
G_DEFINE_TYPE (MyEcho, my_echo, PN_TYPE_NODE)

static void my_echo_receive (PnNode *n, PnMessage *m)
{
    pn_node_emit_message (n, m);   /* pass through */
}

static void
my_echo_class_init (MyEchoClass *klass)
{
    PnNodeClass *nc = PN_NODE_CLASS (klass);
    nc->receive    = my_echo_receive;
    nc->class_name = "Echo";
    nc->icon       = "\xef\x81\xa4"; /* fa-share */
    nc->color      = (GdkRGBA){0.55, 0.65, 0.95, 1.0};
    nc->category   = "Filters";
    nc->has_input  = TRUE;
    nc->has_output = TRUE;
}

static void my_echo_init (MyEcho *self) { (void) self; }

G_MODULE_EXPORT const PnPluginInfo *
pn_plugin_init (PnNodeFactory *factory)
{
    static const PnPluginInfo info = {
        .abi_version = PN_PLUGIN_ABI_VERSION,
        .name        = "EchoPlugin",
        .version     = "1.0.0",
        .description = "Pass-through demo node",
    };
    pn_node_factory_register (factory, MY_TYPE_ECHO);
    return &info;
}

The category field decides the palette group your node joins; the standard values are Sources, Network, Filters and Sinks but a plugin is free to introduce its own group name — pipnode renders any category it sees in registration order.

ABI versioning

Every plugin declares a PN_PLUGIN_ABI_VERSION in its PnPluginInfo. The host refuses to load a plugin whose declared version does not match the value baked into the running pipnode, so a stale plugin sitting in the user's plugin directory cannot crash the process with a silent layout mismatch — pipnode logs a warning and skips it.

The version is bumped whenever an incompatible change to PnNode / PnNodeClass, the factory registration contract, or the plugin entry-point signature ships in a release. Plugins are recompiled and redistributed against the new ABI; an out-of-tree plugin that targets the previous ABI keeps working with the previous pipnode release without needing a patch from us.

Attribution and inspection

Each plugin's PnPluginInfo.name is recorded against every node type it registers. The inspector shows it as the node's provenance; built-in nodes report "Internal". There is no unload path — once a plugin is loaded its .so is pinned in memory for the lifetime of the process, since GTypes registered by the plugin cannot be unregistered. Reloading a plugin during development requires restarting pipnode.

Extending the node settings dialog

The dialog the user sees when double-clicking a node auto-generates one editor row per writable GObject property the node's class chain declares — a GtkEntry for strings, a check button for booleans, a combo for enums, and so on. Plugin-shipped node types get this for free and need no extra _class_init plumbing for the common case.

ABI version 2 adds three optional vfunc slots on PnNodeClass for the cases the auto-generated tab cannot cover on its own: a property whose right widget is not the default (a serial-port path that should pick from a sysfs walk, a file path that should open a file chooser, a value with reactive dependencies on a sibling property), structured configuration that is not naturally a flat property form (a list of rules, a route table — the in-tree Filter and Set rule editors are the worked examples), and configuration that needs more than one notebook tab (a Diagnostics page, a Logs tail, a "Scan for devices" button).

  • build_property_editor — return a custom #GtkWidget for one specific property and let the host fill the other rows. Returning %NULL falls back to the host default.
  • build_class_tab — return a fully custom widget that replaces the auto-generated property tab for this class. Returning %NULL falls back to the introspection-driven default.
  • build_extra_pages — append additional notebook pages beyond the property tab using pn_node_dialog_append_page().

Helpers exposed from <pipnode/pn-node-dialog-helpers.h> (pn_node_dialog_new_property_grid, pn_node_dialog_attach_row, pn_node_dialog_default_editor, pn_node_dialog_append_page) let a partially-custom tab match the host's grid spacing / margins and delegate the rows it does not want to take over back to the host. Worker-thread async operations that should lock the dialog while running can install a read-only boolean property named busy; the host automatically watches it and centres a "Initializing device…" spinner over the notebook while the property is TRUE. The full reference, with worked examples copied from the in-tree PnMeshtastic and PnFilter migrations, lives in the PLUGINS file at the top of the source tree under section 15 (Extending the node settings dialog).

XFCE panel applets

A worksheet does not have to live in its own window. The same flow you build on the canvas can also drive an XFCE panel applet — a small live widget docked in the desktop panel. These applets are deliberately open-ended: an applet is just a thin mirror of one worksheet's panel band, so whatever you can wire up inside pipnode you can surface on the panel. There is no fixed set of panel gadgets to choose from — you can build practically anything the available nodes allow, from a deadline countdown to a thermostat readout, a build-status lamp or a one-click switch, simply by assembling the right nodes in the worksheet behind it. If a node exists for the job, it can run on the panel.

The applet itself is intentionally dumb: it links GTK, GLib, json-glib and libxfce4panel only and embeds no pipnode runtime library, so a misbehaving node or plugin can never take down xfce4-panel. It is a pure D-Bus client — all the real work happens in the engine described next.

The background engine

Each applet instance owns one worksheet, stored as a .json document under ~/.config/pipnode/panel/<unique-id>.json. The flow is not executed by the applet but by a background engine: pipnode-editor launched as a D-Bus service (under the bus name org.pipas.pipnode via --gapplication-service), auto-activated the first time an applet needs it. The engine holds each worksheet in a hidden window whose flow ticks the whole time the panel is up, so the applet keeps updating even though no editor window is visible. The engine is the desktop-session counterpart of the headless pipnode-run tool.

Right-click an applet and choose Properties to open that same running worksheet for editing — you are editing the live flow, not a copy. Closing the editor window autosaves the worksheet and hides it again; the flow keeps running in the engine. Every new applet is seeded with a copy of a shipped starter worksheet so it begins with a working flow rather than a blank sheet.

Bridging a flow to the panel

Two core nodes connect the worksheet to its panel widget:

  • Panel Display (a sink) — its last value is shown on the applet and pushed live. A numeric value is read as seconds remaining and drawn on a tiny seven-segment LED readout as ddd hh:mm:ss (a panel-sized echo of a Countdown node); any other text falls back to a plain label.
  • Panel Input (a source) — each mouse click on the applet emits a message naming the button: the topic click/left / click/right / …, a human-readable sentence on output, and the button number on value.

The applet asks the engine for the widget set and order and follows it as the layout changes; each node's live value arrives keyed by the node's UUID. A click on a Switch toggle flips that one node directly (addressed by UUID) instead of emitting the generic input click, so a single applet can carry both readouts and controls. Snap a Countdown, LED or Switch node onto the panel band in the editor and a matching panel widget appears in the applet.

Building and installing

Panel applets live in the panel-plugins/ subtree (kept separate from the node plugins/ tree). They are an optional, auto-detected part of the build: the subtree is only configured and compiled when libxfce4panel-2.0 ≥ 4.14 and libxfce4util-1.0 are present at configure time, so a machine without XFCE still builds the rest of pipnode unaffected. You can force the decision either way with --enable-panel-plugins or --disable-panel-plugins (the default is auto); --enable errors out if the panel development packages are missing.

An applet must be installed where the running xfce4-panel actually scans — its own module and descriptor directories — not under pipnode's --prefix. The panel only looks in the directories compiled into it, so both paths are derived from libxfce4panel-2.0.pc at configure time ($libdir/xfce4/panel/plugins for the .so module and $datarootdir/xfce4/panel/plugins for the .desktop descriptor). A standard make install puts each piece in the right place; the starter worksheet, by contrast, installs under pipnode's own data dir, which the applet reads by absolute path.

Each applet is built as an XFCE internal panel module: a loadable lib<name>.so the panel dlopen()s on demand, paired with a .desktop descriptor whose X-XFCE-Module key names the library. The only pipnode code an applet embeds is the GTK/Cairo-only panel-widgets convenience library (the LED readout, LED lamp and switch widgets), statically linked — it shares those widgets with the editor's panel-layout view but pulls in none of the node runtime, preserving the crash isolation above.

Adding an applet to the panel

Once installed, the applet appears in the panel's Add New Items… dialog (right-click the panel → Panel → Add New Items…) under its descriptor name. Add it and a fresh worksheet is seeded for that instance; right-click the new applet and choose Properties to open and customise the flow behind it. Add the applet more than once and each copy gets its own independent worksheet, so the same panel can host several unrelated flows side by side.

Desktop layouts

The panel band is not the only surface a flow can drive. Click the “+” button at the right of the tab strip and choose Add Desktop Layout to open the second GUI layout editor: a plain application window you arrange the same widgets in. Where the panel applet squeezes a row of readouts into a strip a few dozen pixels tall, a desktop layout is a window you size yourself, meant for a wall display, a spare monitor or a kiosk screen.

Both editors are the same kind of tab — a layout, not a worksheet sheet. Each document can hold one of each, they open from the same “+” menu, and each carries a “✕” close button in its tab label. Closing one does not discard the arrangement: the placements are document data and are saved with the worksheet, so reopening the layout brings it back exactly as you left it.

The editor shows the window as an outlined rectangle with a mock title bar. Drag any widget into it and it sticks to whichever edge or centre line it comes close to, so rows line up flush or centred without pixel-hunting; widgets cannot be dragged outside the window, because a widget the application would never show is not a placement worth keeping. Above the canvas, the bar sets the two things the application needs to build its window:

  • Window title — the title the application gives the window. Left empty it falls back to the document's own name.
  • Size — the window's width and height in pixels. Resizing it never moves the widgets; anything left outside a shrunken window keeps its coordinates and reappears when the window grows again.

The two layouts are entirely independent maps. The same Countdown node can sit at the left of the panel band and dead centre of the desktop window, and a node placed on one surface need not appear on the other at all — each layout stores only the nodes you actually dragged into it. The same node kinds are representable on both: Countdown, Digital Clock, Label, Matrix 5×7, Numeric, LED, Switch and Inject. Widgets are drawn larger here than on the panel, since a window has the room for it.

Placements are stored relative to the window's content area, so the saved coordinates are exactly what a window needs to paint with. In the saved worksheet they live under desktop_layout, keyed by node UUID, alongside desktop_window (width, height and title).

The desktop application that shows a finished layout — a simple window that displays the widgets where you put them, with no editor around it — is still to be written. What the editor produces today is the layout it will read.

Visualising message flow and node activity

Two optional diagnostic overlays make a running flow legible at a glance: a light travelling along each wire as a message crosses it, and a glow behind a node while it is actually doing work. Both live on the Message Flow page of the Preferences dialog (Edit → Preferences…, then select Message Flow under Worksheet Editor in the category tree). Both are off by default: they are aids for watching a flow, not something you want burning CPU during a long unattended run. The settings are application-wide — they are saved to preferences.json and apply to every open window at once.

  • Wire animation — Animate messages travelling along wires. Every message is drawn as a fast-moving light running along the wire it crosses, so you can see where traffic is flowing and how often. Two dials tune it: Light speed (in worksheet pixels per second) sets how fast each light travels, and Animation interval (in milliseconds) is the redraw period — smaller is smoother but costs more CPU.
  • Node activity — Glow a halo behind a node while it is working. A neon halo bleeds out from behind a node's card for as long as the node is busy, then fades.

The activity halo is deliberately honest: it is driven by each node's real processing state, not by message traffic. A node that merely passes a message through does not light up, and a node that does work without ever emitting a message (a periodic probe that finds nothing changed, a background download, audio playback) does. The halo covers the obvious synchronous case — a node lit while its handler runs — as well as periodic auto-triggered actions (HTTP, weather, host monitors, watchdogs) and nodes that spawn their own worker threads or async callbacks (Text to Speech and Sound while a clip plays, an LLM request in flight, an MQTT or WebSocket connection handshake, image transforms, a sound-pack download). A minimum on-screen linger of about a quarter second keeps even a sub-millisecond blip visible, so a fast node still registers as a brief flash rather than being missed entirely.

A Disabled node never glows (it is doing nothing by definition); a mis-configured node shows its red error body independently of the halo. When neither overlay is enabled the machinery costs nothing — the node-activity wake-up is skipped entirely when no window is listening, which is why a headless pipnode-run never pays for it.

Tips and troubleshooting

  • Red node body, warning glyph. The node is missing required configuration (an empty URL, host or text). Double-click the node to open its property dialog and fill the missing field; the node returns to its normal colour and resumes triggering automatically.
  • Polling vs. events. Auto-triggered nodes (Clock, Ping, HTTP, Temp, Watchdog) emit on every tick. To turn that into an event stream wire them through an Edge filter so only state changes propagate.
  • Inspecting a flow. Drop a Debug node with target = debug view and format = oneliner onto any wire to see what is actually flowing. Switch to JSON when you need to feed the trace into another tool.
  • Saving and sharing. Worksheets are plain JSON files: copy them, diff them, version-control them. The file lists each node's class, properties and the wires between them.
  • Running headless. The companion pipnode-run binary loads a saved worksheet and runs the same message dispatch as the GUI without opening a window — handy for cron, systemd, or any pipeline that just wants the Debug-node lines on stdout. The file is opened read-only, so a scheduled run cannot rewrite it. Pass --timeout=N to stop gracefully after N seconds (otherwise it runs until SIGINT / SIGTERM).
