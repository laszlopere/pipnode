Filter

Group: Filters. Type: PnFilter.

General-purpose gate. Forwards a message iff every configured rule matches the corresponding member of the message's data bag. Rules are ANDed; an empty rule list is vacuously true and lets every message through. The properties dialog lays the rule list out as one row of widgets per rule, with an Add rule button below.

Each rule is a triple of (path, operator, literal). The path selects which member of data to read; common members are preloaded in a combobox (value, success, output, endpoint) and a Custom… entry lets the user reach any other key (e.g. tcp4) or a nested path with dots (e.g. foo.bar). A path that starts with / addresses the message envelope rather than the data bag — /topic is preloaded in the same combobox so a Tasmota / MQTT pipeline can route on the upstream topic (/topic contains "tele/", /topic == "stat/tasmota13/STATUS5") without dropping a Filter rule on the data side. The literal's type combo (number / string / boolean) drives which operators are valid and how the comparison is performed.

Literal typeOperators
number < <= == != >= >
boolean == != (literal picked from a true/false combo)
string == != contains

For string == and != rules, a literal that contains a * or ? is treated as a filename-style glob pattern: * matches any run of characters, ? matches a single character. So /topic == "stat/sonoff19/*" lets through every message whose topic starts with stat/sonoff19/, and /topic == "+/+/STATUS?" matches the numbered STATUS replies (STATUS0 … STATUS9). A literal without wildcards keeps doing byte-exact comparison, so existing rules round-trip unchanged.

A rule whose path is missing on the incoming message — or whose data-bag value's type does not match the literal's type — fails, and the message is dropped.

The rule list is persisted as a single string property (rules) holding the JSON array form so it round-trips through the worksheet save/load path unchanged.
