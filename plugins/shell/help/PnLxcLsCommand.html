Lxc Ls Command

Group: Shell. Type: PnLxcLsCommand.

Auto-triggered runner that executes sudo lxc-ls -f every period seconds and emits one message per run on its output port. sudo and lxc-ls are looked up on PATH; the command is spawned on a worker thread so the GUI never blocks.

Setup: the host user must have passwordless sudo configured for lxc-ls — the spawn happens with no controlling tty, so a password prompt would just fail. A typical /etc/sudoers.d/pipnode-lxc-ls drop-in looks like youruser ALL=(root) NOPASSWD: /usr/bin/lxc-ls. When sudo fails the emitted message still arrives, but with data.success = false and data.output carrying sudo's diagnostic.

Like Df Command and Free Command, the emitted message carries the parsed table inline so a downstream Table View can render it without an intermediate Table Model filter. lxc-ls -f's default output has single-token headers (NAME, STATE, AUTOSTART, GROUPS, IPV4, IPV6, UNPRIVILEGED) and fixed-width whitespace-padded data rows, so the parser is a plain whitespace split per line with the column count derived dynamically from the header (a future lxc-ls release that adds or removes a column needs no code change). Trailing tokens past the last header column are folded into the last cell so a wider-than-expected last column doesn't spawn a phantom extra column.

The emitted message carries:

  • data.success — true when sudo lxc-ls -f exited with status 0, false otherwise.
  • data.output — the combined stdout and stderr of the run, verbatim.
  • data.table — the parsed table in the standard { "header": { "cells": [...] }, "rows": [ { "cells": [...] }, ... ] } shape. Each cell is a JSON object with at minimum { "text": "...", "name": "..." }; the Table View sink reads only text and ignores unknown members, so the extra name is transparent to it.

Cell names follow the shape <row>.<column>. The column id comes from the sanitised header word ("NAME" → name, "IPV4" → ipv4, "UNPRIVILEGED" → unprivileged); the row id comes from the sanitised first-column value (the container NAME: "dns2" → dns2), with leading and trailing underscores stripped. The header row's row id is the literal header.

Caveat: a container with multiple comma+space separated IPs in the IPV4 or IPV6 column (e.g. "192.168.1.1, 10.0.0.1") tokenises as two tokens under whitespace splitting and shifts subsequent columns one slot right. The default single-IP case — the most common one — parses cleanly.

The remote login defaults to your ambient SSH setup: the local desktop account and whatever key your ssh-agent or ~/.ssh already provides, trusting the host key on first sight. To reach the host as a different account, on a non-standard port, with a specific identity file, or under a stricter host-key policy, attach an SSH Login credential from the node's SSH Login picker (the auth-profile property). The credential says how to log in; the host field still says where. With none selected the node keeps the original passwordless-SSH behaviour.

PropertyDescription
host Where to run sudo lxc-ls -f. Default: the empty string — the local machine, whose name appears as a grey hint in the settings entry. An empty value, localhost, 127.0.0.1 and ::1 all run locally (clearing the field leaves it empty rather than reverting to localhost). Any other value (a hostname or user@host) routes the run through ssh -o BatchMode=yes -o ConnectTimeout=5; a working passwordless key for that host is required since BatchMode disables every interactive prompt. The passwordless-sudo requirement still applies on the remote machine.
period Seconds between executions.
auth-profile Optional SSH Login credential supplying the remote account, port, identity file and host-key policy. Empty (the default) follows the primary SSH Login profile, or — when none is configured — the node's ambient-key behaviour. Stored in the host vault, never in the worksheet file. Separate from host, which still selects where to connect.
