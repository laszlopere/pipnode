Tasmota Probe

Group: Tasmota. Type: PnTasmotaProbe.

The discovery half of the Tasmota concentrator. Sits between an MQTT Source and an MQTT Sink and turns the passive telemetry stream into an active, per-device status poll — with no external network scan. It watches every message go by, learns which Tasmota devices exist from the topics they publish on, and emits a Status query for each one so the device reports its configuration and runtime info.

The replies do not come back through this node; the device publishes them on stat/<device>/STATUS (and STATUS1 … STATUS11). Wire a parallel branch — MQTT Source → Tasmota Concentrator → Debug — to collect and present them.

Why per-device, not one broadcast

A command published to Tasmota's tasmotas group topic is acted on by every device, but Tasmota deliberately suppresses the MQTT reply for group (and fallback) topic commands — so a single cmnd/tasmotas/Status yields zero stat/+/STATUS responses. MQTT wildcards (#, +) don't help: they are illegal in a publish topic, and * is just a literal. To read information back from every device you must address each one individually. This node automates exactly that loop — it discovers the devices and fires one request per device. (The group topic tasmotas itself is never probed, for the same reason.)

How it discovers devices

The <device> segment is parsed out of the envelope topic of the three Tasmota topic families — tele/<device>/…, stat/<device>/… and cmnd/<device>/…. Any other traffic sharing the upstream MQTT Source is ignored. The node keeps a live set of every device it has ever seen:

  • A newly-seen device is probed promptly — the first message that names it triggers a probe.
  • An already-known device is never re-probed more often than the interval (see below), no matter how much telemetry it sends in the meantime.
What gets sent

For each device that is due, the inbound message is reshaped in place into a Tasmota command: the envelope topic becomes cmnd/<device>/Status and data.payload is set to the numeric section selected by the request property, so the device sees exactly Status <n>. This is the same shape Tasmota Status Request produces, ready for a downstream MQTT Sink to publish with no intervening Format / Rewrite node. A Status query is strictly read-only.

Configuration
PropertyDescription
request Which Status section each discovered device is asked for — Everything (Status 0) for the full report, or one specific section (Network (Status 5) for IP / hostname / MAC, MQTT (Status 6), and so on). Default: Everything (Status 0).
interval Minimum seconds between two probes of the same device. A newly-seen device is always probed immediately; this only rate-limits the re-probe of a device already known. Default: 300 (five minutes). Set to 0 to probe on every message that names the device.
Output shape

The node emits only probe commands — it never forwards the telemetry it observed, so its output wires straight to the MQTT Sink without echoing sensor traffic. Each emitted message carries:

MemberValue
envelope topic cmnd/<device>/Status
data.payload String "0" … "11" — the selected section, the shape MQTT Sink's default payload path publishes as raw bytes without quoting.
data.success true on every emitted probe.
data.device The discovered device the probe is addressed to.
data.output Human-readable summary, e.g. sonoff19: probe Status 0.
Wiring example
MQTT Source (topic = tele/#, stat/#)
    → Tasmota Probe (request  = Everything (Status 0),
                          interval = 300)
        → MQTT Sink (url = tcp://mqtt.homelab.local:1883)

MQTT Source (topic = stat/+/STATUS#)
    → Tasmota Concentrator
        → Debug

As telemetry from each device flows through the first MQTT Source, Tasmota Probe discovers the device and publishes cmnd/<device>/Status 0 via the MQTT Sink; each device answers on stat/<device>/STATUS…, which the parallel branch collects with Tasmota Concentrator and shows in Debug.
