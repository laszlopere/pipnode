Ambient Temperature

Group: Host monitoring. Type: PnAmbient.

Auto-triggered probe that samples a host's ambient (chassis, motherboard, chipset) temperature sensors every period seconds and emits a single aggregated value (in degrees Celsius) as data.value. Sibling of CPU Temperature — same property shape, same emitted envelope, same aggregation semantics. The difference is the set of sensors picked up off the host: this node targets the ambient readings rather than the silicon package readings, so a worksheet can graph room/chassis warmth on its own axis without having to filter CPU sensors out.

Sources scanned (in order of preference):

  1. /sys/class/hwmon/hwmonN/ directories whose name is acpitz — the ACPI Thermal Zone, which on most consumer hardware is the motherboard sensor.
  2. Fallback: /sys/class/thermal/thermal_zoneN/ directories whose type is acpitz, has the pch_ prefix (Platform Controller Hub — chipset, which on a passively-cooled board tracks ambient closely), matches INT340N Thermal (Intel DPTF participant sensors, often skin temperature), or is one of gen_thermal, TZ00, TZ01 (vendor zones seen on some laptops). The thermal-zone fallback is only consulted when the hwmon scan turned up nothing, so the same physical sensor is not double-counted through both interfaces.

When hostname is empty or "localhost" the sensor files are read off the local filesystem directly; any other value is treated as a remote host and the sample is fetched over passwordless SSH (ssh -o BatchMode=yes … hostname sh -c <snippet>) on a worker thread, so an unreachable target cannot freeze the GUI.

The emitted message carries data.value (aggregated ambient temperature in °C), data.average, data.min, data.max, data.count (number of sensors that contributed), data.unit (always "°C"), data.hot (label of the warmest sensor — useful when running with aggregation = "average" and you still want to know which zone is the outlier), data.aggregation (the active mode as the string "average" or "maximum"), data.readings (a JSON array of {label, value} objects, one per sensor), data.host (normalised to "localhost" for the local path), data.success, and data.output (a one-line summary — either the aggregated reading with sensor count, or the failure reason).

A successful sample with zero matching sensors is treated as a failure (data.success = false, data.output = "no ambient temperature sensors found") rather than silently emitting 0.0. This typically means the host has neither an acpitz hwmon entry nor a matching thermal zone — common on minimalist ARM SoCs and on some hypervisor guests; on bare-metal x86 the acpitz zone is almost always present.

Superio chips (Nuvoton nct67xx, ITE it87, Winbond w83, Fintek f71) also expose chassis sensors, but they mix them with CPU- and fan-tach-derived readings under per-chip labels, so picking them up by hwmon name alone would pollute the aggregation. Users on such boards are better served by the thermal-zone fallback, or should add their specific chip to the matched-name list once they have confirmed which tempN_input on it is the chassis sensor.

PropertyDescription
hostname Host whose ambient sensors to read. Defaults to "localhost"; an empty string is treated the same. Any other value is used as the SSH target — passwordless authentication must already be set up (BatchMode=yes is forced so the probe never prompts for a password).
aggregation How the per-zone ambient readings are collapsed into the single number on data.value: "average" reports the arithmetic mean across every matched sensor, "maximum" reports the hottest single sensor (handy for spotting a blocked vent or a sunlit panel). In either mode the unaggregated data.average, data.min, data.max and data.readings members are always populated, so a downstream filter can consult the other view without reconfiguring this node.
period Seconds between samples. The default is 5 s — ambient temperatures only move on the order of minutes (thermal mass of the chassis and the room itself), so polling faster mostly buys repeated identical readings. 5 s matches the other host-monitoring nodes so they can all share a downstream graph without periods drifting against each other.
