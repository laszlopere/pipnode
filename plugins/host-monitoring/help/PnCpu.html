CPU

Group: Host monitoring. Type: PnCpu.

Auto-triggered probe that samples /proc/stat every period seconds and emits the CPU busy percentage as data.value (0–100), computed as the per-tick delta of the kernel's cumulative jiffy counters between two consecutive samples. Unlike System Load — which reports the run-queue-length load average, a proxy that does not distinguish "100% of one core" from "saturated 16 cores" — this node reports the actual fraction of wall-clock time the CPU spent in non-idle states.

The percentage is built from the conventional accounting buckets: busy = user + nice + system + irq + softirq + steal, idle = idle + iowait, total = busy + idle, with the guest / guest_nice columns the kernel exposes since 2.6.24/2.6.33 intentionally not double-counted (they are already included in user / nice, and top/htop follow the same rule). iowait is also emitted separately on data.iowait so a worksheet can graph it as its own series.

The first sample after construction (or after a hostname / core change) carries value = 0 and a "warming up" note in data.output: a real reading needs two samples.

The sample comes from /proc/stat directly when hostname is empty or "localhost"; any other value is treated as a remote host and the file is fetched over passwordless SSH (ssh -o BatchMode=yes … hostname cat /proc/stat) on a worker thread, so an unreachable target cannot freeze the GUI.

core picks which row to measure. An empty string (the default) reads the aggregate "cpu" line — a sum across every core that the kernel maintains for us, so data.value represents the whole machine. A numeric value ("0", "1", …) selects the matching per-core row ("cpu0", "cpu1", …) so a worksheet can graph a single core in isolation.

The emitted message carries data.value (busy percentage), data.idle, data.iowait (the two non-busy buckets), data.unit ("%"), data.core (the row that was read: "cpu" for the aggregate, "cpu0" / "cpu1" / … for a single core), data.host, data.success, and data.output (a one-line human summary). When the SSH probe fails the remote stderr or the spawn error message is folded into data.output; when the file was read but no row matched the configured core, data.output explains that explicitly.

The remote login defaults to your ambient SSH setup: the local desktop account and whatever key your ssh-agent or ~/.ssh already provides, trusting the host key on first sight. To reach the host as a different account, on a non-standard port, with a specific identity file, or under a stricter host-key policy, attach an SSH Login credential from the node's SSH Login picker (the auth-profile property). The credential says how to log in; the hostname field still says where. With none selected the node keeps the original passwordless-SSH behaviour.

PropertyDescription
hostname Host whose /proc/stat to read. Defaults to "localhost"; an empty string is treated the same. Any other value is used as the SSH target — passwordless authentication must already be set up (BatchMode=yes is forced so the probe never prompts for a password). Changing this property mid-flight discards the previous sample so the next emitted value is the "warming up" zero rather than a spurious cross-host delta.
core Which /proc/stat row to measure. Empty string (the default) reads the aggregate "cpu" line; a numeric value ("0", "1", …) selects the matching per-core row. Changing this property mid-flight discards the previous sample (same reason as for hostname).
period Seconds between samples. The default of 2 s keeps the per-tick delta well above the jiffy-resolution noise floor while still feeling responsive in a downstream Graph.
auth-profile Optional SSH Login credential supplying the remote account, port, identity file and host-key policy. Empty (the default) follows the primary SSH Login profile, or — when none is configured — the node's ambient-key behaviour. Stored in the host vault, never in the worksheet file. Separate from hostname, which still selects where to connect.
